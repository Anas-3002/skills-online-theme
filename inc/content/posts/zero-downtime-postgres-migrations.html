Schema migrations are the one deploy step that can take down an otherwise healthy database. On a live PostgreSQL table, a DDL statement behaves nothing like the same statement on an empty test database: it acquires a table-level lock that either blocks every query or almost none. The gap is the difference between a millisecond catalog update and a multi-minute table rewrite holding ACCESS EXCLUSIVE while it copies every row.

This article covers the mechanics PostgreSQL documents, the version boundaries that change the advice, and the patterns — concurrent index builds, fast column defaults, constraint validation, batched backfills, and expand/contract — that let you change schema on large tables while the application keeps serving traffic. Every behavioural claim is pinned to the current PostgreSQL manual or the release note that introduced it.

Which DDL statement takes which lock

PostgreSQL has eight table-level lock modes. The key fact is that ALTER TABLE acquires ACCESS EXCLUSIVE unless a subform explicitly notes otherwise, and a command with multiple subcommands takes the strictest lock any of them needs. ACCESS EXCLUSIVE conflicts with every other lock, including ACCESS SHARE — so it blocks plain SELECT, not just writes.

A statement's lock mode is often the same whether it is fast or slow; how long the lock is held is what turns a safe migration into an incident.

The lock queue is the real outage

The failure people hit most often is not a slow rewrite; it is a fast statement that waits. An ALTER TABLE must acquire ACCESS EXCLUSIVE, and if any transaction already holds a conflicting lock — a long analytics SELECT, or a session idle inside a transaction — the ALTER waits. Every new query that needs a conflicting lock then queues behind it, because a pending exclusive lock request blocks later conflicting acquisitions. A statement that would have run in microseconds can freeze the table for as long as the slow query runs.

The fix is to make DDL fail fast rather than poison the queue: set a lock_timeout on every DDL step.

BEGIN;
SET LOCAL lock_timeout = '3s';
SET LOCAL statement_timeout = '15s';
ALTER TABLE orders ADD COLUMN status text;
COMMIT;

lock_timeout aborts a statement that waits too long for a lock; statement_timeout caps total runtime and suits the scan-based steps such as validation and backfills. Run the migration in a retry loop: if it times out, the table was busy, so try again rather than forcing the lock.

Treat a lock timeout as a normal outcome, not an error. A harness that retries on lock_timeout will eventually find a quiet window and never hold the queue.

CREATE INDEX CONCURRENTLY, and why it cannot run in a transaction

A plain CREATE INDEX takes a SHARE lock: reads continue, but every write blocks for the duration of the build. CREATE INDEX CONCURRENTLY avoids that by taking only SHARE UPDATE EXCLUSIVE, which does not block ordinary reads or writes. In exchange it is slower: PostgreSQL performs two table scans in separate transactions and waits for transactions that could modify or use the index to finish.

Because it spans multiple transactions internally, CREATE INDEX CONCURRENTLY cannot run inside a transaction block — the manual states this explicitly. Migration tools that wrap every migration in a transaction must mark this step non-transactional, or run it as its own script outside a BEGIN.

-- Must NOT be inside BEGIN/COMMIT.
CREATE INDEX CONCURRENTLY idx_orders_customer_id
    ON orders (customer_id);

If the build is interrupted — a deadlock, a timeout, or a unique violation — it leaves an invalid index behind. An invalid index is ignored by the planner but still adds write overhead. Find them and clean up:

SELECT indexrelid::regclass AS invalid_index
FROM pg_index
WHERE NOT indisvalid;

-- Recovery: drop and retry, or rebuild in place (PostgreSQL 12+).
DROP INDEX CONCURRENTLY idx_orders_customer_id;
-- or
REINDEX INDEX CONCURRENTLY idx_orders_customer_id;

Adding columns and defaults without a rewrite

On PostgreSQL 11 and later, ADD COLUMN with a non-volatile default does not rewrite the table. The default is evaluated once, stored in the table's metadata, and returned for existing rows on access, so the ALTER TABLE is a fast catalog update even on a table with hundreds of millions of rows. The PostgreSQL 11 release notes describe this as allowing ALTER TABLE "to add a column with a non-null default without doing a table rewrite".

The trap is a volatile default: the manual states that one such as clock_timestamp(), a stored generated column, an identity column, or a domain type carrying constraints will cause the entire table and its indexes to be rewritten — under ACCESS EXCLUSIVE, so reads block as well as writes.

ADD COLUMN ... DEFAULTRewrite?
0, 'pending', true, now()No — catalog update only
gen_random_uuid(), random(), clock_timestamp()Yes — full table rewrite
GENERATED ALWAYS AS (...) STORED, GENERATED ... AS IDENTITYYes — full table rewrite

Note that now() takes the fast path because it is stable, not volatile: it is evaluated once for the statement, so every existing row gets the same timestamp. For a distinct value per row, do not use a volatile default in ADD COLUMN; add the column, set a default, and backfill.

-- Fast on PostgreSQL 11+: constant default, no rewrite.
ALTER TABLE orders ADD COLUMN status text NOT NULL DEFAULT 'pending';

-- Per-row value without a rewrite: add, then set the default for new rows.
ALTER TABLE orders ADD COLUMN api_key uuid;
ALTER TABLE orders ALTER COLUMN api_key SET DEFAULT gen_random_uuid();

ALTER COLUMN ... SET DEFAULT on an existing column only changes what future inserts receive; it never touches existing rows, so it never rewrites.

Adding NOT NULL safely

ALTER COLUMN ... SET NOT NULL ordinarily scans the whole table to verify no nulls exist. Since PostgreSQL 12 that scan is skipped when a valid CHECK constraint already proves no nulls are possible. The safe sequence: add the check as NOT VALID (skips the scan), validate it under a lock that does not block reads or writes, then set NOT NULL — which now skips its own scan — and drop the redundant check.

-- 1. Instant: no scan, enforced for new rows only.
ALTER TABLE orders
    ADD CONSTRAINT orders_api_key_not_null
    CHECK (api_key IS NOT NULL) NOT VALID;

-- 2. Scans under SHARE UPDATE EXCLUSIVE; reads and writes continue.
ALTER TABLE orders VALIDATE CONSTRAINT orders_api_key_not_null;

-- 3. Skips its own scan because the valid CHECK proves no nulls (PostgreSQL 12+).
ALTER TABLE orders ALTER COLUMN api_key SET NOT NULL;

-- 4. Drop the now-redundant check.
ALTER TABLE orders DROP CONSTRAINT orders_api_key_not_null;

The same NOT VALID to VALIDATE CONSTRAINT pattern applies to foreign keys, which take only a SHARE ROW EXCLUSIVE lock and skip the initial scan.

Batched backfills with throttling

Backfilling a column in a single UPDATE creates one long transaction: it holds locks, generates a wall of dead tuples, and can bloat the table. Do it in batches that each commit quickly, keyed on a stable column such as the primary key.

-- One batch; run repeatedly until it touches 0 rows.
UPDATE orders
SET status = 'pending'
WHERE id IN (
    SELECT id FROM orders
    WHERE status IS NULL
    ORDER BY id
    LIMIT 10000
);

Drive it from the shell so each batch is its own transaction and the loop can be throttled and resumed:

while true; do
  tag=$(psql -At -c "
    WITH batch AS (
      SELECT id FROM orders WHERE status IS NULL LIMIT 5000
    )
    UPDATE orders o SET status = 'pending'
    FROM batch WHERE o.id = batch.id;")
  n=${tag##* }          # psql -At returns the tag, e.g. 'UPDATE 5000'
  echo "updated $n rows"
  [ "$n" = "0" ] && break
  sleep 0.2             # let autovacuum and replicas keep up
done

Keep batches small enough to commit in well under a second, throttle to protect replicas and autovacuum, and always filter on the predicate that still needs work (WHERE status IS NULL) so re-running the loop is idempotent.

Expand/contract: rolling schema changes out across deploys

Old and new versions of your application run at the same time during a rolling deploy, so a schema change must be split into backward-compatible steps. The expand/contract pattern does exactly this:

  1. Expand. Add the new column as nullable, with a default for new rows. Old code ignores it; new code starts writing it.
  2. Dual-write. Deploy code that writes both the old and the new representation, so no data is lost regardless of which version handles a request.
  3. Backfill. Fill historical rows in batches, while both columns stay in sync.
  4. Switch reads. Deploy code that reads only the new column.
  5. Contract. Once no code reads the old column, stop writing it and drop it in a later deploy.

Never rename a column in place as a single step: a rename is invisible to old code, which fails the moment it runs. Add the new column, migrate the data, then drop the old one.

Always have a rollback plan

Design every step to be revertible without a data restore. The cleanest rollback for a forward-compatible migration is simply to stop using the new column and redeploy the previous application version — nothing is lost because the old data is still there. That is why the contract step comes last and in its own deploy: dropping a column is fast but irreversible, so postpone it until the new path has run in production for a while.

Two habits make rollback real: keep each migration small enough that its reverse is obvious, and rehearse the down path on a copy of production first. If a step cannot be safely reversed — a destructive DROP COLUMN, a data type change that rewrites rows — isolate it as the final, deliberate step.

If you cannot describe how to undo a migration step in one sentence, the step is too big.
