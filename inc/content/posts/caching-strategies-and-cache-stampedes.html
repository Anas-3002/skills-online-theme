Every cache is a bet that serving a slightly stale answer is cheaper than computing a fresh one. The bet usually pays: latency drops, expensive queries disappear, and a struggling database gets breathing room. But it is asymmetric. A cache that helps at 500 requests per second can become the component that takes down the whole system at 5,000, because the moment a popular key expires, every request that missed it stampedes the database at once.

This article covers the decisions that decide whether a caching layer holds under load: which read and write pattern you pick and what each one breaks, how to set TTLs so expiries do not synchronise, how to defend against stampedes, negative caching, how invalidation and versioned keys work, how to handle hot keys, and how to measure whether the cache is earning its keep.

The four patterns and their failure modes

Most production caching uses one of four patterns, differing in where the cache sits and what happens on a write.

PatternRead pathWrite pathMain failure mode
Cache-asideApp checks cache; on miss reads the database and populates the cacheApp writes the database, then deletes or updates the cacheRace between a slow reader repopulating stale data and a concurrent writer
Read-throughCache library or proxy loads from the database on missApp writes the database onlyFirst access to any key is always a miss; cold-start cost
Write-throughCache always has the value after a successful writeApp writes cache and database in the same requestWrite latency includes the database; cache failure blocks writes
Write-behindCache always has the valueApp writes the cache and returns; the database flush is asynchronousData loss or divergence if the cache dies before it flushes

Cache-aside is the default because the application keeps control and a cache outage degrades to slower reads rather than failed writes. Read-through is cache-aside behind an interface, which removes repeated logic but hides the miss. Write-through keeps the cache and database consistent at the cost of coupling write latency to both. Write-behind is fastest to write and the only pattern that can lose data.

Pick the pattern by asking what happens on a write when the cache is unavailable. If the answer is "the write fails", you are running write-through whether you meant to or not.

Cache-aside in practice

The classic helper checks the cache, falls back to the source, and repopulates. Two hazards matter: blocking forever on contention, and overwriting a fresher value with a stale one.

def get_user(user_id):
    key = f"user:{user_id}:v{SCHEMA_VERSION}"
    cached = cache.get(key)
    if cached is not None:
        return deserialize(cached)

    value = load_from_db(user_id)          # the expensive call
    if value is None:
        cache.set(key, NEGATIVE, ex=NEG_TTL)     # negative caching
    else:
        cache.set(key, serialize(value), ex=ttl_with_jitter())
    return value

The subtle bug is the read-modify-write race. Reader A misses, reads version 1, and is paused. Writer B updates the database to version 2 and deletes the key. Reader A wakes, writes version 1 back, and the cache now holds stale data for a full TTL. Deleting rather than updating on write narrows the window but does not close it. The robust fixes are a versioned key, so a stale write lands under an old name that is never read, or a short TTL on the repopulation write to bound the window.

TTL and jitter

TTL is the safety net for every invalidation you forgot. Set the value and its expiry together so they cannot drift:

SET user:42:profile "{\"name\":\"ada\"}" EX 300
TTL user:42:profile             # seconds remaining; -1 no expiry, -2 missing
EXPIRE user:42:profile 600 GT   # extend only if the TTL is below 600s

The failure mode is synchronised expiry. If a batch job loads ten thousand keys with the same TTL, they all expire together and every one becomes a database hit in the same second. The fix is jitter, for example ex = base * (1 + random.uniform(0, 0.1)). Treat TTL as the maximum acceptable staleness for that data class, not as a substitute for invalidation on write: profile data might tolerate minutes, a balance seconds, an inventory count none.

Stampede protection: single-flight, locks, and stale-while-revalidate

A cache stampede, or thundering herd, happens when a hot key expires and many concurrent requests all miss and recompute the same value. Three defences, usually combined:

  • Single-flight (request coalescing): in-process, only the first caller loads; the rest wait on the same future, collapsing N concurrent misses into one database read per process.
  • Distributed lock: across processes, one worker recomputes while others wait briefly or serve stale. Redis supports this with an atomic conditional set that includes a mandatory expiry:
SET lock:user:42 <unique-token> NX PX 5000  # acquire only if absent; auto-expire in 5s
# ... recompute and repopulate ...
DEL lock:user:42                            # release (ideally only if the token still matches)

NX makes the set succeed only when the key is absent, and PX guarantees release even if the holder crashes; a lock without an expiry is a deadlock waiting for its first process failure. Some systems instead use probabilistic early expiration, where each reader refreshes slightly before the TTL with a probability that rises as expiry nears.

Stale-while-revalidate is the highest-leverage option. Keep the value plus a freshness deadline. When a request finds the value past freshness but before a hard expiry, it returns the stale value immediately and triggers a single-flighted background refresh. Readers never wait for the database. This is the semantics HTTP defines for stale-while-revalidate, and it is the pattern to reach for when blocking on a miss is unacceptable. The trade-off is explicit: you serve stale for the refresh window so no stampede reaches the database.

Under load, the answer to "the cache is stale" is almost never "block every request until it is fresh". Serve stale, refresh once, in the background.

Negative caching and versioned-key invalidation

A cache only helps if misses are rare. Requests for keys that do not exist always miss, which is the attack known as cache penetration: random nonexistent IDs, each one reaching the source. Negative caching stores the "not found" result with a short TTL so repeat lookups are served from the cache. Two rules keep it safe: keep the negative TTL short, because a key missing a moment ago may exist now, and never negative-cache an authorization decision, because a stale denied or allowed is a security bug, not a performance trade-off.

The invalidation pattern that scales is versioned keys. Put a version token in every key, for example user:42:v7:profile. To invalidate everything for a user or a schema, increment the version. Every later read looks up the new key and misses once; old entries are never read again and expire on their own. This turns a potentially enormous SCAN and DEL sweep into one counter increment, and it avoids the race where a delete and a concurrent repopulation disagree. When you must delete, prefer delete-on-write over update-on-write: writing a computed value risks caching a stale computation, while deleting lets the next reader compute fresh.

Hot keys and sharding

A key receiving a large fraction of all traffic is a hot key, and capacity does not help because all of that load lands on one shard. Mitigations, in rough order of preference:

  1. Add a local in-process cache in front of Redis for the hottest read-mostly keys, with a short TTL, removing most traffic from the network and the shared cache. Redis supports server-assisted client-side caching, where the server tracks cached keys and sends invalidation messages so the local copy stays correct enough without polling.
  2. Shard the key by appending a random suffix and reading from one of N replicas of the same value, spreading a read-hot key across nodes. This works for reads only.
  3. Replicate the hot key so reads fan out across multiple instances.

The limitation is that sharding and replication solve read hotspots, not write hotspots, because a counter or lock must agree on a single value. For write-heavy hot keys, aggregate in the application and flush periodically.

What a cache must never be used for

A cache is an optimisation that must be safe to lose. Do not treat it as durable storage unless you have designed and tested the recovery path, because write-behind without that discipline loses writes when the cache dies. Do not use it as a job queue, since its eviction policy can discard work items silently. Do not use it as a lock without an expiry and a unique token, because a crashed holder then blocks everyone forever. Do not cache authorization decisions or per-tenant data without a deliberate answer to revocation and isolation. And do not let a cache hide a missing database index: a cache that fixes a slow query masks a schema problem that resurfaces the moment the cache is cold.

Measuring whether the cache is helping

Hit rate is the metric everyone reaches for and the easiest to misread. A 95% hit rate sounds excellent until the 5% of misses are all on the most expensive keys, so the misses dominate database load and the p99. Track hit rate by key class, and always pair it with the miss penalty.

  • Hit rate, sliced by key class: an overall rate hides a cold, expensive class behind a hot, cheap one.
  • Latency percentiles at the application boundary: p50, p95, p99 for cached and uncached paths. The mean is useless; a cache's value shows up in the tail, or fails to.
  • Eviction and expiry rates: rising evictions mean the workload exceeds the cache and you are thrashing. Compare evictions against expirations.
  • Stampede signals: lock contention, single-flight waits, and database load right after large TTL expiries. A database QPS spike on the minute is a synchronised-expiry problem.
  • Cost: memory and node count weighed against the database capacity the cache lets you remove.

Measure latency where the user experiences it, and test the cold path deliberately: a cache never observed empty in production has an unmeasured failure mode.
