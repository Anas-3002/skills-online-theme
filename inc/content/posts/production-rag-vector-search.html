Retrieval-augmented generation is easy to prototype and hard to keep good. A weekend project that answers questions over a handful of PDFs will impress you; the same architecture against a corpus that changes daily, with users who file support tickets when an answer is wrong, tends to quietly rot. The failure is rarely the model. It is the retrieval layer: chunks that no longer match their documents, embeddings generated by a model you replaced six months ago, and a ranking step that looked fine on twenty hand-picked queries.

This article is about the engineering that keeps a RAG pipeline honest over time: how to chunk, how to combine keyword and vector retrieval, how to re-rank, how to tune a pgvector/HNSW index without guessing, how to build an evaluation harness you actually run, and the operational failure modes that bite teams in production. Every number here is either a documented default or a range you should measure for yourself — treat the tuning advice as a procedure, not a recipe.

Chunking: structure first, size second

The chunk is the unit of retrieval and the unit of context. Get it wrong and no amount of index tuning will save you: a chunk that splits a table from its caption, or cuts a procedure in half, will retrieve as noise. Before you tune chunk size, chunk on structure. Split on document-native boundaries — headings, list items, code blocks, table rows — and treat those as the atomic units. Only then decide whether adjacent units should be merged.

Size and overlap

There is no universal chunk size. The useful heuristic is that a chunk should be self-contained enough to answer a question without its neighbours, and small enough that one retrieved chunk does not crowd out three better ones. Overlap exists to protect against a sentence that straddles a boundary, but generous overlap multiplies storage and inflates the chance that near-duplicate chunks dominate the top-k results. Measure instead of guessing: hold a labelled query set, change one variable (size, then overlap), and watch retrieval recall move.

Keep the context attached

Whatever the chunk size, store metadata alongside it: document id, section path, source URL, last-modified timestamp, and the content hash of the exact text that was embedded. That hash is what makes incremental re-embedding, drift detection, and citation possible later. A chunk row that cannot tell you which version of a document it came from is a chunk you will eventually have to throw away.

Hybrid retrieval: keyword and vector, not either/or

Dense vector search handles paraphrase and semantic similarity well; it is weak on exact identifiers, rare terms, error codes, and product names, because those are low-frequency strings that carry little semantic signal. Lexical search — PostgreSQL full-text search, BM25, OpenSearch — does the opposite. Production systems run both and fuse the results. PostgreSQL's documentation describes GIN indexes as the preferred index type for full-text search, with GiST as the lossy alternative, and you can keep the vector column and the tsvector column in the same table and query both in a single statement.

-- Fuse lexical and vector rankings with Reciprocal Rank Fusion
WITH lexical AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY ts_rank_cd(tsv, query) DESC) AS rank
  FROM chunks, plainto_tsquery('english', :q) query
  WHERE tsv @@ query
  LIMIT 50
),
semantic AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> :vec) AS rank
  FROM chunks
  ORDER BY embedding <=> :vec
  LIMIT 50
)
SELECT COALESCE(l.id, s.id) AS id,
       COALESCE(1.0 / (60 + l.rank), 0) + COALESCE(1.0 / (60 + s.rank), 0) AS score
FROM lexical l
FULL OUTER JOIN semantic s ON l.id = s.id
ORDER BY score DESC
LIMIT 20;

Reciprocal Rank Fusion (RRF) combines rank positions rather than raw scores, which is why it works across two systems whose scores are not on the same scale. The constant 60 is the value used in the original RRF formulation; it dampens the influence of the very top ranks so that a single confident-but-wrong system cannot dominate the fused list. Fuse the two, then let the re-ranker decide.

Re-ranking: the cheapest quality win

Retrieval is recall-oriented; the model's prompt is precision-oriented. A cross-encoder re-ranker reads the query and each candidate chunk together and scores relevance directly, which is more accurate than comparing independently produced embeddings. The pattern is: retrieve a wide candidate set with hybrid search, re-rank it, keep the top handful, and only then build the prompt. This also lets you keep the vector index cheap and fast while recovering quality at the ranking stage.

A retriever that returns the right document at rank 40 is a working retriever. A re-ranker that lifts it to rank 3 is what makes the answer correct.

pgvector and HNSW index tuning

Exact nearest-neighbour search scans every vector; approximate indexes like HNSW trade a little recall for a large speed gain, which is why they matter at scale. In pgvector, an HNSW index is controlled by two build-time parameters and one query-time parameter:

  • m — the maximum number of connections per graph layer. More connections mean better recall and a larger index; the documented default is 16.
  • ef_construction — the size of the candidate list when building the graph. Larger values mean a higher-quality graph and a slower build; the documented default is 64.
  • ef_search — set at query time. Raising it scans more candidates, improving recall at the cost of latency, which makes it the knob you tune to hit a latency budget.
-- Build the index once; tune ef_search per query
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- Increase recall for a specific query
SET hnsw.ef_search = 100;

SELECT id FROM chunks ORDER BY embedding <=> :vec LIMIT 10;

The trade-off is unavoidable: recall versus index size versus build time versus query latency. Build the index after a bulk load rather than maintaining it during one, measure recall against a brute-force baseline on a sample of queries, and move the knobs one at a time. If exact search returns the same top-k as your index for most queries, the index is good enough and further tuning is wasted effort.

An evaluation harness, not a vibe check

You cannot keep a pipeline from degrading if you never measure it. Before launch, build a small labelled set of real questions with the passages that should answer them, and separate retrieval from generation so a bad answer can be attributed to one or the other. Retrieval metrics — recall@k, mean reciprocal rank, and normalised discounted cumulative gain — are cheap, deterministic, and catch most regressions. Generation metrics need either human labels or a model as judge; frameworks like Ragas exist to standardise reference-free metrics such as faithfulness and answer relevance, and embedding benchmarks like MTEB give you a principled way to choose an embedding model rather than picking one by reputation.

Re-run the harness on every change to chunking, the embedding model, the index parameters, or the re-ranker. A change that improves both your gut feeling and your harness is real; a change that improves only your gut feeling is a regression waiting to be discovered by a user.

Operational failure modes

Stale embeddings

The most common silent failure: the embedding model is upgraded, or the corpus changes, and the index now mixes vectors from two different models or misses recent documents. Vectors from different models are not comparable, so the results are subtly wrong rather than obviously broken. Version your embedding model in the schema, re-embed the whole corpus when it changes, and give each chunk the content hash of its source so you can find the ones that need refreshing.

Chunk drift

Source documents change, and chunks are cut at boundaries that no longer align. A paragraph appended at the top of a document shifts every downstream chunk, invalidating whichever hashes were tied to the old layout. The fix is deterministic chunking — the same input text under the same chunker must produce the same chunks — so an incremental re-index touches only what changed instead of the entire corpus.

Prompt injection through retrieved content

Content retrieved from the web, from user uploads, or from any source you do not fully control is untrusted input, and it reaches the model inside the same context window as your instructions. OWASP's guidance on prompt injection is explicit that retrieval does not remove the risk: an attacker can plant text in a document that instructs the model to ignore its instructions, leak data, or call a tool. Treat retrieved text as data, never as instructions; delimit it clearly; keep the model's authority over tools and side effects narrow; and validate outputs against the source before acting on them. There is no single prompt that makes this safe — it is a design constraint, not a filter.

Putting it together

A production RAG pipeline is a data pipeline with a model at the end. Chunk on structure and keep provenance, retrieve with both lexical and vector signals, re-rank the candidates, tune the index against a measured recall target, and run the evaluation harness on every change. None of it is glamorous, and all of it is what separates a demo that degrades from a system that holds up.
